## 🎯 核心改進

### 1. 按天限制功能實施 ✅

**問題**：跨天未解決的警報會更新同一個警報，無法按天追蹤問題發生情況。

**解決方案**：

- 同一天內，同一個問題更新同一個警報
- 跨天後，創建新的警報（即使問題相同）

**實施效果**：

```
改進前：
2025-01-06 → 創建警報（PM2.5 = 51µg/m³）
2025-01-07 → 更新警報（同一個警報）❌
2025-01-08 → 更新警報（同一個警報）❌

改進後：
2025-01-06 → 創建警報（PM2.5 = 51µg/m³）
2025-01-06 → 更新警報（PM2.5 = 52µg/m³）✅ 同一天
2025-01-07 → 創建新警報（PM2.5 = 53µg/m³）✅ 跨天
```

**效益**：

- ✅ 可以按天追蹤問題發生情況
- ✅ 統計分析更準確（每日問題數量）
- ✅ 警報歷史更清晰

### 2. 時間處理統一化 ✅

**問題**：時間計算不一致，導致 Toast 顯示的警報在頁面看不到。

**根本原因**：

- `TimeRangePicker` 組件使用**本地時間**
- `alert-log.vue` 初始化使用**UTC 時間**
- 後端使用**UTC 時間**
- 導致時間範圍計算不一致

**解決方案**：

- 創建統一的時間工具函數 `app/utils/dateUtils.ts`
- 所有時間計算統一使用 UTC 時間
- 與後端保持一致

**優化效果**：

| 項目         | 優化前       | 優化後    | 改善 |
| ------------ | ------------ | --------- | ---- |
| 時間計算函數 | 2 處重複     | 1 處統一  | -50% |
| 時間標準     | 混用本地/UTC | 統一 UTC  | ✅   |
| 與後端一致性 | ❌ 不一致    | ✅ 一致   | ✅   |
| 時區問題     | ⚠️ 可能出現  | ✅ 已解決 | ✅   |

### 3. 前後端一致性修正 ✅

**問題**：前端類型定義與後端實際行為不一致。

**發現的問題**：

- 前端類型說 `updated_at: string | null`，但後端資料庫設置為 `NOT NULL DEFAULT CURRENT_TIMESTAMP`
- 前端需要處理 null，但實際上永遠不會發生

**解決方案**：

- ✅ 修正類型定義：`updated_at: string`（不再是 `string | null`）
- ✅ 優化顯示邏輯：如果 `updated_at` 與 `created_at` 相同，顯示「與創建時間相同」
- ✅ 簡化 `formatDateTime` 函數（不需要處理 null）

## 🔧 技術實現

### 按天限制實現

**核心邏輯**：

```javascript
// 查詢現有 active 警報時，添加日期限制
WHERE source = ?
  AND source_id = ?
  AND alert_type = ?
  AND status = 'active'
  AND created_at >= todayStart  // 當天開始時間（UTC）
  AND created_at < todayEnd      // 當天結束時間（UTC）
```

**關鍵函數**：

- `getTodayDateRange()` - 獲取當天的開始和結束時間（UTC）
- `findExistingActiveAlert()` - 查詢現有的 active 警報（支持按天限制）

### 統一時間處理

**新增工具**：`app/utils/dateUtils.ts`

**功能**：

- `getTodayDateRangeUTC()` - 獲取當天的 UTC 時間範圍（與後端一致）
- `getTimeRangeUTC(preset)` - 獲取各種預設時間範圍（UTC）
- `formatDateLocal(date)` - 格式化日期為本地顯示格式（YYYY/MM/DD）
- `formatDateInput(date)` - 格式化日期為 input 格式（YYYY-MM-DD）
- `formatDateTime(dateString)` - 格式化日期時間為本地顯示格式（YYYY/MM/DD HH:mm）
- `formatDate(dateString?)` - 格式化日期（支持 null，返回 "-"）

**使用場景**：

- `TimeRangePicker` 組件 - 統一使用 UTC 時間計算
- `alert-log.vue` 頁面 - 統一使用 UTC 時間初始化
- 所有頁面的日期時間顯示 - 統一使用工具函數
- 與後端時間計算保持一致

### 代碼重構

## 🔄 工作流程

### 警報創建與更新流程

1. **前置檢查**
   - 檢查是否有被忽視的警報
   - 查詢現有 active 警報（按天限制）

2. **更新或創建決策**
   - 同一天內：更新現有警報（severity 升級或 message 變化）
   - 跨天後：創建新警報

3. **WebSocket 推送**
   - `alert:new` - 新警報創建
   - `alert:updated` - 警報更新
   - `alert:count` - 未解決警報數量更新

### 自動解決機制

- **閾值警報**：感測器數值恢復正常時自動解決
- **設備連線警報**：設備恢復連線、錯誤計數重置為 0 時自動解決

### 時間篩選流程

1. **初始化**：使用 UTC 時間計算「今天」的範圍
2. **用戶選擇**：TimeRangePicker 使用 UTC 時間計算選定的時間範圍
3. **篩選邏輯**：使用 `created_at` 進行時間範圍篩選
4. **一致性**：前端與後端都使用 UTC 時間，確保一致性

## ⚠️ 發現並修復的問題

### 問題 1：Toast 顯示但頁面看不到 ✅ 已修復

**原因**：

- 時間範圍篩選與警報顯示不同步
- 頁面初始化使用 UTC 時間，但 TimeRangePicker 使用本地時間
- 導致時間範圍計算不一致

**解決方案**：

- 統一使用 UTC 時間計算
- 創建統一的時間工具函數
- 確保前端與後端時間計算一致

### 問題 2：前後端類型定義不一致 ✅ 已修復

**原因**：

- 前端類型說 `updated_at: string | null`
- 但後端資料庫設置為 `NOT NULL DEFAULT CURRENT_TIMESTAMP`
- 導致前端需要處理 null，但實際上永遠不會發生

**解決方案**：

- 修正類型定義：`updated_at: string`
- 簡化顯示邏輯，移除不必要的 null 檢查
- 優化時間顯示：如果 `updated_at` 與 `created_at` 相同，顯示「與創建時間相同」

### 問題 3：代碼重複 ✅ 已修復

**原因**：

- 時間格式化函數在多個頁面重複實現
- 狀態檢查函數位置不當
- 維護困難，容易出現不一致

**解決方案**：

- 統一時間格式化函數到 `dateUtils.ts`
- 統一狀態檢查函數到 `alertUtils.ts`
- 所有頁面使用統一的工具函數

## 📋 頁面顯示內容

### 時間欄位說明

**創建時間（`created_at`）**：

- ✅ 必填欄位，不會為 null
- ✅ 警報首次創建的時間
- ✅ 用於時間範圍篩選（按天限制的依據）
- ✅ 創建後不會改變
- ✅ 格式：`YYYY/MM/DD HH:mm`

**更新時間（`updated_at`）**：

- ✅ 永遠不會為 null（資料庫設置為 `NOT NULL DEFAULT CURRENT_TIMESTAMP`）
- ✅ 警報最後更新的時間
- ✅ 當警報內容（severity、message）更新時會改變
- ✅ 當警報狀態變更時也會改變
- ✅ 新創建時與 `created_at` 相同（或極其接近）
- ✅ 格式：`YYYY/MM/DD HH:mm`（如果與創建時間相同，顯示「與創建時間相同」）
- ❌ 不用於時間範圍篩選

**解決時間（`resolved_at`）**：

- ✅ 可選，僅已解決警報有值
- ✅ 格式：`YYYY/MM/DD HH:mm`

**忽視時間（`ignored_at`）**：

- ✅ 可選，僅已忽視警報有值
- ✅ 格式：`YYYY/MM/DD HH:mm`

### 時間差異場景

| 場景       | 創建時間         | 更新時間                           | 說明                    |
| ---------- | ---------------- | ---------------------------------- | ----------------------- |
| 新創建警報 | 2026/01/12 08:00 | 2026/01/12 08:00（與創建時間相同） | 新創建，尚未更新        |
| 同一天更新 | 2026/01/12 08:00 | 2026/01/12 10:30                   | severity 升級或數值更新 |
| 已解決警報 | 2026/01/12 08:00 | 2026/01/12 17:32                   | 狀態變更為 resolved     |
